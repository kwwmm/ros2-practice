# Practice 07 — Turtlesim Goal Navigation with ROS 2 Actions

An end-to-end ROS 2 Jazzy exercise that uses **a custom Action interface, live pose feedback, velocity commands, and proportional control** to move a Turtlesim turtle to a requested `(x, y)` location. The client can also cancel a moving goal.

> This README explains both **how to run** the exercise and **why the system works**. For a line-by-line Korean analysis of the actual Python code used in this practice, see [CODE_WALKTHROUGH.md](CODE_WALKTHROUGH.md).

## 1. Objective

Implement an Action-based navigation task with these observable behaviors:

1. Send a target coordinate from a Python Action Client.
2. Validate and accept or reject the goal on the Action Server.
3. Read the turtle's current pose from `/turtle1/pose`.
4. Calculate distance and heading error and publish `Twist` commands to `/turtle1/cmd_vel`.
5. Stream position and remaining distance as Action feedback.
6. Stop and report a result when the turtle reaches the goal, when a goal is canceled, or when the task times out.

This practice connects the concepts of **Topic** (continuous data), **Action** (long-running goal), and **feedback control** (using observations to decide commands).

## 4. Communication Overview

```text
                     Action: /move_to_goal
  +-------------------+       Goal (x, y)        +----------------------+
  | move_client.py    | -----------------------> | move_server.py       |
  | Action Client     | <----------------------- | Action Server        |
  +-------------------+   Feedback and Result    +----------------------+
           |                                               ^        |
           | Cancel request                                |        | Twist
           +----------------------------------------------> |        v
                                               Pose  /turtle1/pose
                                                  +-----------------+
                                                  |    turtlesim    |
                                                  +-----------------+
                                                        ^
                                                        |
                                                 /turtle1/cmd_vel
```

In precise terms, Turtlesim **publishes** `/turtle1/pose`, which the Action Server **subscribes** to; the server **publishes** `/turtle1/cmd_vel`, which Turtlesim **subscribes** to.

| Channel | Type | Direction | Purpose |
| --- | --- | --- | --- |
| `/move_to_goal` | `turtle_move_interfaces/action/MoveToGoal` | Client ↔ Server | Goal, Feedback, Result, Cancel |
| `/turtle1/pose` | `turtlesim/msg/Pose` | Turtlesim → Server | `x`, `y`, `theta` |
| `/turtle1/cmd_vel` | `geometry_msgs/msg/Twist` | Server → Turtlesim | `linear.x`, `angular.z` |

### What makes Action different from Topic or Service?

- A **Topic** carries a stream of updates; pose observations and velocity commands are good examples.
- A **Service** typically exchanges one request and one response.
- An **Action** represents a goal that takes time: it has acceptance/rejection, progress feedback, a terminal result/status, and cancellation support.

The server uses Topic communication *inside* the implementation of an Action goal. These are complementary mechanisms, not alternatives.

## 5. Custom `MoveToGoal.action` Interface

```text
float32 target_x
float32 target_y
---
bool success
float32 final_x
float32 final_y
---
float32 current_x
float32 current_y
float32 distance_remaining
```

The two `---` separators create three distinct sections:

| Action section | Fields | Interpretation |
| --- | --- | --- |
| Goal | `target_x`, `target_y` | Desired Turtlesim coordinate |
| Result | `success`, `final_x`, `final_y` | Success flag and final observed pose |
| Feedback | `current_x`, `current_y`, `distance_remaining` | Intermediate position and Euclidean distance |

The result has both an application-level `success` field and an Action **status** (`SUCCEEDED`, `CANCELED`, or `ABORTED`). These are different: the status reports how the Action ended, while `success` is a field defined by this project.

## 6. How Navigation Works

Let the current turtle position be `(x, y)`, current heading be `theta`, and target be `(x_goal, y_goal)`.

**Position error and distance**

```text
dx = x_goal - x
dy = y_goal - y
distance = sqrt(dx² + dy²)
```

**Desired heading and wrapped heading error**

```text
target_angle = atan2(dy, dx)
angle_error = atan2(sin(target_angle - theta), cos(target_angle - theta))
```

The second `atan2` normalizes the error approximately to `[-π, π]`, avoiding unnecessary long rotations across the `±π` boundary.

**Proportional velocity control in this implementation**

```text
if abs(angle_error) > 0.35 rad:
    linear.x = 0                  # rotate first
else:
    linear.x = min(1.5, distance) # move faster when farther away

angular.z = clamp(4.0 * angle_error, -2.0, 2.0)
```

The server publishes commands about every `0.1 s` in its execution loop. These are simple P-style control rules, not a full PID controller. The movement terminates when `distance < 0.15` Turtlesim coordinate units. There is a `60 s` timeout safeguard, and a cancellation check in the loop.

**Important limitations:** This is a teaching controller in a simulator. It does not do obstacle avoidance, path planning, motion acceleration limiting, or robust fault recovery. Feedback may arrive irregularly, and the reported distance can temporarily increase during turning.

```bash
source /opt/ros/jazzy/setup.bash

```

### Step 2 — Build the interface package

From the practice directory:

```bash
cd ~/ros2_practice/07_turtlesim_action

```

`colcon list` should include `turtle_move_interfaces`. The build produces the `build/`, `install/`, and `log/` directories. `source install/setup.bash` makes generated interfaces discoverable in the current terminal.

### Step 3 — Verify the generated type

```bash
ros2 interface show turtle_move_interfaces/action/MoveToGoal
python3 -c "from turtle_move_interfaces.action import MoveToGoal; print('Action import successful')"
```

Expected import check:

```text
Action import successful
```

Rebuild after changing `MoveToGoal.action`, `CMakeLists.txt`, or relevant package metadata. Direct edits to the standalone Python scripts do **not** require another colcon build here.

## 8. Run the Complete System

Use **three separate terminals**. Keep the first two running while sending goals.

### Terminal 1 — Start Turtlesim

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=13
ros2 run turtlesim turtlesim_node
```

A window containing a turtle should appear.

### Terminal 2 — Start the Action Server

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=13
cd ~/ros2_practice/07_turtlesim_action
source install/setup.bash
python3 -u move_server.py
```

Expected server startup message:

```text
Turtle Move Action Server started.
```

### Terminal 3 — Send a goal

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=13
cd ~/ros2_practice/07_turtlesim_action
source install/setup.bash
python3 -u move_client.py 8.0 8.0
```

The turtle turns and moves toward `(8.0, 8.0)`. The client prints a running distance and then a final position and Action status.

The argument syntax is:

```bash
python3 move_client.py TARGET_X TARGET_Y [--cancel-after SECONDS]
```

The client exits after receiving a terminal result or rejecting the goal. The server continues waiting for future goals.

## 9. Verified Results

The following observations were **reported from the actual practice terminal**, not simulated output.

### Goal completion

Command:

```bash
python3 -u move_client.py 8.0 8.0
```

| Measure | Observed value |
| --- | --- |
| Start | approximately `(5.54, 5.54)` |
| Target | `(8.0, 8.0)` |
| Last feedback | `(7.97, 7.87)`, remaining distance `0.14` |
| Final position | `(7.99, 7.86)` |
| Terminal status | `Goal succeeded.` |

The reported goal status is consistent with the configured `0.15` arrival threshold. This is **tolerance-based arrival**, not exact coordinate equality.

### Goal cancellation

Command:

```bash
python3 -u move_client.py 2.0 2.0 --cancel-after 3
```

| Measure | Observed value |
| --- | --- |
| Initial position | approximately `(7.99, 7.86)` |
| Target | `(2.0, 2.0)` |
| Initial remaining distance | `8.38` |
| Cancellation response | `Cancel accepted.` |
| Final reported position | `(6.72, 6.80)` |
| Terminal status | `Goal canceled.` |

The final position differs from the position at which the request was sent because cancellation is **asynchronous**: the server must receive the request, check the cancellation state, and send a zero-velocity command.

### Goal rejection — expected behavior, not yet verified

```bash
python3 -u move_client.py 15.0 15.0
```

The server is written to reject values outside the range `0.5 ≤ x, y ≤ 10.5`, so this **should** display `Goal rejected.`. No terminal output confirming this test was supplied when this README was written.

## 11. Troubleshooting

| Symptom | Likely reason | Check |
| --- | --- | --- |
| `install/setup.bash: No such file or directory` | Workspace has not been built successfully | Run `colcon build --symlink-install` at the practice root |
| `No module named 'turtle_move_interfaces'` | Interface not built or current terminal not sourced | `source install/setup.bash`; run import check |
| `XML or text declaration not at start of entity` | A blank line or text precedes the XML declaration | The first character of `package.xml` must be `<` in `<?xml ...?>` |
| Client exits silently | File is empty or `main()` is never called | Check `wc -l move_client.py` and the file's final lines |
| Client waits for server indefinitely | Server not running or DDS domain mismatch | Check `ros2 action list -t`, server terminal and domain IDs |
| No movement | Turtlesim missing, pose not received or command not published | Check `/turtle1/pose` and `/turtle1/cmd_vel` |

An actual troubleshooting sequence in this practice was: fix `package.xml` first-line formatting → build interface successfully → confirm Python import → discover an empty `move_client.py` → save the client code → verify goal completion and cancellation.

## 12. What I Learned

- How to define a custom ROS 2 Action and generate the Python interface with ROSIDL.
- How to separate long-running goal management (Action) from continuous sensing and control (Topics).
- How Action Goal/Feedback/Result/Cancel flows work in a live simulator.
- How pose error is translated into bounded linear and angular velocity commands.
- Why `MultiThreadedExecutor` and callback groups matter for receiving pose updates while an Action executes.
- Why a valid ROS 2 build is not sufficient if a standalone client script is empty or not saved.

## Conclusion

This practice successfully connected a custom ROS 2 Action to closed-loop Turtlesim motion. **Goal completion and cancellation were verified** with terminal results. Goal rejection is implemented but remains to be separately tested. The same high-level architecture can later support a mobile robot with real localization and motion interfaces, after adding appropriate safety and navigation capabilities.
